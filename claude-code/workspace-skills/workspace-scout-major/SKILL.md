# workspace-scout-major

複数の git リポジトリを直下（深さ1）にクローンした「ワークスペースディレクトリ」を対象に、
opt-in 済みの全リポジトリを横断して読み、2つ以上のリポジトリにまたがり、かつリポジトリ間に
依存順序がある（どちらかを先に変更しないと安全に進められない）アーキテクチャ級の改善候補を探す。
見つけた候補は、[improvement-scout-major](../../skills/improvement-scout-major/SKILL.md) と
同じ「milestone ＋ 依存順のタスク分解」の思想で、関与する各リポジトリ自身の `Proposed` に
milestone とタスクを起票する。成果物は各リポジトリに起票される milestone とタスクだけである。
このスキルの中でコードは変更しない。

## workspace-dispatch / workspace-scout との違い

`workspace-dispatch`・`workspace-scout` は「opt-in 済みの各リポジトリへ順に `cd` し、既存スキルの
手順をリポジトリごとに独立に繰り返す」薄いオーケストレーション層であり、リポジトリ間の関係を
一切見ない。対して本スキルは、**調査フェーズをワークスペース全体で1回だけ横断して行う**。
あるリポジトリだけを読んで判断するのではなく、opt-in 済みの全リポジトリを一度に読み、
リポジトリをまたぐ構造的な依存（共有ライブラリの契約、複数リポジトリで重複した処理、
リポジトリ間のデータ/スキーマの整合性、リリース順序の前提など）を探す専用の観点リストを使う。

**各リポジトリの `.backlog/` はワークスペース全体で共有しない。** 1つの候補につき、関与する各
リポジトリにそれぞれ独立した milestone を起票する（backlog の milestone はリポジトリをまたげない
ため、「1つの巨大な cross-repo milestone」は作らない）。対応関係は、milestone の名前を揃える
ことと、全関連タスクに付ける共通ラベル `cross-repo:<スラッグ>` だけで追跡する。

## improvement-scout-major との違い

| | improvement-scout-major | workspace-scout-major |
| --- | --- | --- |
| 調査範囲 | 1リポジトリ内 | opt-in 済みの全リポジトリを横断して1回で調査 |
| 起票の閾値 | 1リポジトリ内で複数タスクへの分割が要る規模か | 2つ以上のリポジトリにまたがり、かつ依存順序があるか |
| milestone | 1候補＝1リポジトリに1 milestone | 1候補＝関与する各リポジトリにそれぞれ1 milestone（同名または対応が分かる名前） |
| リポジトリ内の依存関係 | `--dep TASK-<n>` | 同じく `--dep TASK-<n>`（リポジトリ内は変わらない） |
| リポジトリ間の依存関係 | 該当なし | `--dep` は使えない（backlog が起票時に対象IDをそのリポジトリの `.backlog/` 内でのみ検証するため）。下流タスクの description に「## クロスリポジトリ依存」節を書く |
| 順序の担保 | dispatch が `Dependencies` の未完了 `To Do` を自動除外 | **自動強制なし。** 人間が各リポジトリで承認順序を守って `To Do` に上げる |

1リポジトリに閉じる規模の候補（既存 `improvement-scout-major` の対象）は、本スキルでは起票しない。
探索中に見つかった場合は、そのリポジトリ向けの `improvement-scout-major`/`improvement-scout` 候補
として報告するだけにとどめる。

## 前提

- このスキルは `bin/setup-improvement-loop --workspace <ワークスペースディレクトリ>` を実行した
  ワークスペースディレクトリの直下（`.claude/skills/workspace-scout-major`）に配置される。
  カレントディレクトリをそのワークスペースルートとして扱う。
- 対象となるのは、ワークスペース直下（深さ1）のサブディレクトリのうち、(a) git リポジトリで
  あり、(b) `<リポジトリ>/.claude/skills/improvement-scout-major` が実在解決するシンボリック
  リンクとして存在する（＝ `bin/setup-improvement-loop`（`--workspace` 無し）でそのリポジトリ
  自身に improvement ループをセットアップ済み）ものだけである。この判定基準以外の新規マーカー
  ファイルは無い。
- 対象外のリポジトリ（未セットアップ、または git リポジトリでないディレクトリ）は黙って対象
  から外れる。エラーにはしない。

## 引数

`[--count N]` を任意で受ける。指定がなければ候補は1候補（＝1相関スラッグ、関与する全リポジトリの
milestone・タスクを含む）まで起票する。`--count` を超えた候補は起票せず、報告に列挙する。

## 1. 対象リポジトリを列挙する

散文で `git` や `find` を組み立てず、決定論的なスクリプトを使う。

```bash
.claude/skills/workspace-scout-major/scripts/list-target-repos
```

標準出力に、opt-in 済みリポジトリの絶対パスが1行1件・ソート済みで並ぶ。0件なら何も出力されない。

- **2件未満（0件または1件）の場合**：起票せず、「クロスリポジトリの改善候補を探すには
  improvement-scout-major に opt-in 済みのリポジトリが2つ以上ワークスペース直下に必要である」
  旨を報告して終了する（手順2には進まない）。1件だけ opt-in 済みの場合は、そのリポジトリ名を
  添え、単一リポジトリの探索であればそのリポジトリで直接 `improvement-scout-major` を実行できる
  旨も伝える。
- **2件以上の場合**：列挙された全リポジトリを対象に手順2へ進む。

## 2. 観点に目を通す

観点リストは `.claude/skills/workspace-scout-major/viewpoints.md` にある。まず読む。
`claude-code/skills/improvement-scout-major/viewpoints.md`（単一リポジトリ内のモジュール境界が前提）
とは別物であり、こちらは複数リポジトリをまたぐ契約・重複・データ整合性・リリース順序に特化した
観点である。4観点すべての「問い」を対象ワークスペースに当ててみて、2つ以上のリポジトリにまたがり
依存順序がある強い候補があるかを見る。無理に各観点から候補を出す必要はない。該当なしのまま終わる
観点があってよい。

## 3. 各リポジトリの既存タスク・milestoneと照合する

同じ内容が既にどこかのリポジトリで追跡されていないか、調査に入る前に確認する。手順1で列挙した
各リポジトリへ順に `cd` し、milestone 一覧とキーワード検索で確認する。

```bash
backlog milestone list --plain
backlog search "<キーワード>" --plain
backlog search --modified-file <対象パス> --plain
```

- `backlog task list --labels` はラベル文字列の完全一致でしか絞り込めない（`cross-repo` のような
  接頭辞では該当タスクが1件も返らない）ため、この時点ではまだ確定していない相関スラッグを前提にした
  絞り込みには使わない。上記のキーワード検索・`--modified-file` 検索と milestone 一覧の目視で
  重複を確認する。
- 同じ趣旨の milestone・タスクが既にあれば、その候補は起票しない。`Proposed` のまま残っている候補も
  対象に含めて数える。
- 手順6.1で相関スラッグの候補を決めた後、そのスラッグが既に使われていないかを最終確認したい場合は
  `backlog task list --labels 'cross-repo:<候補スラッグ>' --plain`（完全一致の文字列を渡す）で
  個別に確認してよい。ただしこれは補助的な確認であり、上記のキーワード検索・milestone 一覧に代わる
  主たる重複検出手段ではない。
- 各リポジトリの処理を終えたら、次のリポジトリへ進む前にワークスペースルートへ戻る。

## 4. 調査する

`workspace-dispatch`/`workspace-scout` のように1リポジトリずつ独立に処理するのではなく、
列挙された全リポジトリを横断して読む。先に全体像を掴んでから、観点ごとの「問い」に答える。

各リポジトリについて最低限次を読む。

```bash
git -C <リポジトリのパス> log --oneline -30
git -C <リポジトリのパス> ls-files
```

- 各リポジトリの README、CLAUDE.md、エントリポイント、設定/契約定義箇所（公開する API・CLI・
  データフォーマットの定義、他リポジトリが参照している可能性のあるディレクトリ構造や設定ファイル）
  を読む。
- あるリポジトリが別のリポジトリの名前・パス・出力形式・環境変数名などを直接参照・言及していないか
  探す（コード内の文字列リテラル、README の記述、CI 設定、依存関係の宣言ファイルなど）。
- 見つけた手がかりをもとに、参照されている側のリポジトリを実際に開いて、その参照が現在も正しいか
  （宣言と実態が一致しているか）を確認する。

起票しないもの：

- 好みのリファクタ、命名やスタイルの揺れ、抽象化の追加。
- 「〜かもしれない」で終わる推測。確認できないなら確認する。確認できないなら候補から落とす。
- 1リポジトリに閉じる規模のもの（`improvement-scout-major`/`improvement-scout` に譲る）。
- 観点リストの「除外」に該当するもの。

候補ごとに、確認できることは確認する。該当ファイルを両方のリポジトリで読み切る、
`git log -- <path>` で経緯を見る。意図的にそうなっている可能性を排除してから候補に残す。

## 5. 選別する

起票の閾値は「2つ以上の opt-in 済みリポジトリにまたがり、かつ依存順序（どちらかを先に変更しないと
安全に進められない）がある規模か」。

- 2つ以上のリポジトリにまたがり、片方の変更が完了してからでないともう片方が安全に進められない
  ＝候補として起票する。
- 1リポジトリに閉じる（他リポジトリの変更を前提にしない）＝起票せず、報告でそのリポジトリ向けの
  `improvement-scout-major`（複数タスクへの分割が要る規模の場合）または `improvement-scout`
  （1タスクで閉じる規模の場合）の候補として挙げる。
- 複数リポジトリにまたがってはいるが、順序を問わずどちらからでも独立に進められる（依存順序が
  無い）＝このスキルの対象外。各リポジトリで個別に `improvement-scout-major`/`improvement-scout`
  の候補として挙げる。

優先度の目安（milestone・配下タスク共通、既存 `improvement-scout-major` と同じ基準）：

- `High`：現状のまま放置すると壊れやすい構造上の欠陥、または既に事故が起きている構造。
- `Medium`：特定の変更を行おうとするたびに複数リポジトリを手で合わせる必要があり、今後も繰り返し
  踏まれる。
- `Low`：今は動くが、将来この前提のまま片方のリポジトリが変わると破綻する芽。

影響を言葉にできない候補は `Low` にせず落とす。`--count` に届かないなら届かないまま報告する。
数を埋めるための起票をしない。

## 6. milestone とタスクを起票する

候補ごとに次を行う。1候補＝関与する各リポジトリに1つずつの milestone（backlog の milestone は
リポジトリをまたげないため）。

### 6.1 相関スラッグを決める

候補の内容が分かる短い英数字スラッグ（例: `shared-auth-contract`）を1つ決める。以降、関与する
全リポジトリのラベル `cross-repo:<スラッグ>` と milestone のタイトルに一貫して使う。

### 6.2 関与する各リポジトリで前提を確認する

これから初めて起票を行うリポジトリでは、`claude-code/skills/improvement-scout-major/SKILL.md` の
「1. 前提を確認する」と同じ内容を、そのリポジトリのディレクトリで行う。

```bash
backlog instructions overview
backlog instructions task-creation
backlog config get statuses
backlog config get types
backlog config get priorities
backlog milestone add --help
backlog task create --help
```

`Proposed` が `statuses` に無ければ `.backlog/config.yml`（または `backlog/config.yml`）の
`statuses` に先頭で追加する（`backlog config set` では変更できない）。上のブロックの
`backlog config get` と `backlog instructions` は、`backlog config list` と同様に `--plain` を
受け付けない。渡すと `error: unknown option '--plain'` を出して終了コード1で終わるため、
`--plain` 無しで実行する（対話 UI にはならない）。`--plain` が必要なのは `backlog task list` /
`backlog task view` / `backlog search` / `backlog milestone list` の側であり、こちらは付けないと
対話 UI が起動してセッションが止まる。判断に迷うコマンドは `backlog <サブコマンド> --help` の
Input schema に `--plain` があるかで確かめる。

### 6.3 各リポジトリで milestone を起票する

関与するリポジトリへ順に `cd` し、それぞれで対応する milestone を起票する。タイトルは全リポジトリで
同一、または一目で対応が分かる名前にする（例: `repo-a` 側は「共有認証コントラクトの刷新（発行側）」、
`repo-b` 側は「共有認証コントラクトの刷新（利用側）」）。milestone 自体はラベルを持てないため、
対応関係の追跡は名前の一致と、配下タスクに付ける `cross-repo:<スラッグ>` ラベルに委ねる。

```bash
backlog milestone add '<何を再編・移行するかが分かる名詞句（他リポジトリ側と対応が分かる名前）>' \
  -d '## 現状
<file:line を挙げて、いま何がどうなっているか。このリポジトリ側の状態>

## 問題
<この規模で直す必要がある理由。1タスクで閉じない根拠>

## 期待する結果
<milestone全体が完了したときに満たされるべき状態。実装方法は書かない>

## クロスリポジトリ対応
このmilestoneは相関スラッグ `cross-repo:<スラッグ>` で <他の関与リポジトリ名> の
「<対応するmilestone名>」と対応する。依存順序: <どちらのリポジトリを先に完了させる必要があるか>。

## 確認したこと
<読んだファイル、実行したコマンドとその結果（複数リポジトリを横断して確認した内容を含む）>'
```

出力される milestone の ID・タイトルを控える。以降のタスク起票で `-m` に渡す。

### 6.4 各リポジトリで実装可能粒度に分解し、タスクを起票する

各リポジトリの milestone 配下で、`improvement-scout-major` の 6.2/6.3 と同じ手順を踏む。

- 各タスクは1回の `improvement-work` 実行で完結する粒度にする。大きすぎるならさらに分ける。
- **同一リポジトリ内の依存だけ** `--dep TASK-<n>` を使う。依存グラフを先に組み立て、DAG になって
  いるか確認してから、前提タスクを先に起票し、実際に割り振られた ID を控える。
- **リポジトリをまたぐ依存には `--dep` を使わない。** backlog は起票時に対象IDをそのリポジトリの
  `.backlog/` 内でのみ検証するため、他リポジトリのタスクIDを渡すと起票自体が失敗する。代わりに、
  上流リポジトリの変更を前提とする下流リポジトリのタスクには、description に次の節を追加する。

```
## クロスリポジトリ依存

このタスクは <上流リポジトリ名>（milestone「<上流milestone名>」の TASK-<n> 「<上流タスクタイトル>」）
の完了を前提とする。<上流タスクが完了する前にこのタスクを着手すると何が起きるか、具体的に>。
上流タスクが Done になり、契約が新しい形になったことを確認してから、このタスクを To Do に上げること。
```

上流側のタスクIDは、上流リポジトリで先に起票を終えてから控える（起票の順序は上流→下流を守る。
下流タスクの description に書く上流タスクIDが未確定のまま起票しない）。

```bash
backlog task create '<何をどうするかが分かる動詞句>' \
  -s Proposed \
  --type <bug|chore|enhancement|feature|docs|spike> \
  --priority <High|Medium|Low> \
  --labels 'audit,viewpoint:<slug>,cross-repo:<スラッグ>' \
  --modified-file <根拠のパス> \
  -m '<6.3で控えたこのリポジトリのmilestoneのIDまたはtitle>' \
  --dep TASK-<同一リポジトリ内の先行タスクのID> \
  -d '## 現状
<file:line を挙げて、いま何がどうなっているか>

## 問題
<どの条件で誰が何に困るか>

## 期待する結果
<満たされるべき状態。実装方法は書かない>

## クロスリポジトリ依存
<下流タスクの場合のみ。上記の節をここに書く。上流タスク・milestoneに依存しない（このリポジトリ内で
先行して着手できる）タスクにはこの節を書かない>

## 確認したこと
<読んだファイル、実行したコマンドとその結果>' \
  --ac '<検証可能な条件>' \
  --ac '<検証可能な条件>' \
  --plain
```

規約は `improvement-scout-major` の 6.3 の規約（単一引用符、`-s Proposed` の明示、
`--modified-file` の付与、受入基準は振る舞いで書く 等）をそのまま継承する。加えて：

- `--labels` には必ず `cross-repo:<スラッグ>` を含める。milestone 配下の全タスクに付け、
  リポジトリをまたいで `backlog task list --labels 'cross-repo:<スラッグ>' --plain` で追跡できる
  ようにする。
- 起票の順序は、依存される側（上流）のリポジトリのタスクから先に起票する。下流タスクの
  description に書く上流タスクIDは、実際に起票されて確定したIDを使う。

## 7. 報告する

関与した全リポジトリを1つの横断ビューとして報告する。

1. 相関スラッグと候補の概要、根拠の `file:line`（複数リポジトリにまたがる場合はリポジトリ名を
   併記する）。
2. リポジトリごとに、起票した milestone（ID・タイトル）と、その配下のタスク一覧（ID・タイトル・
   優先度・観点・同一リポジトリ内の依存関係）。
3. **リポジトリ間の承認順序を明示する。** 「まず `<上流リポジトリ>` の `<milestone名>` 配下のタスクを
   `To Do` に上げて `Done` まで進めてから、`<下流リポジトリ>` の `<milestone名>` 配下のタスクを
   `To Do` に上げること」という形で、どのリポジトリのタスクを先に完了させ、どのリポジトリのタスク
   を後から承認すべきかを書く。
4. 承認はリポジトリごとに個別に行う必要がある旨を添える（`backlog task edit TASK-<n> -s "To Do"`
   はそのタスクがあるリポジトリのディレクトリで実行する）。**この承認順序は人間の運用に委ねられて
   おり、自動では強制されない**旨を明記する。
5. milestone に値しなかった、または依存順序が無く1リポジトリに閉じていた小粒度の指摘を箇条書きで
   示し、対象リポジトリでの `improvement-scout-major`/`improvement-scout` の起票候補として挙げる。
6. 件数上限（`--count`）で落とした候補があれば、件数と概要を書く。

milestone・タスク本文と報告の言語は会話の言語に合わせる。既存タスクがあるならその言語に合わせる。

## 禁止事項

`claude-code/skills/improvement-scout-major/SKILL.md` の禁止事項を、対象とする全リポジトリに対して
そのまま継承する。

- `.backlog/`（または `backlog/`）配下の md を直接編集しない。追加も更新もアーカイブも `backlog`
  CLI 経由で行う。config.yml は例外で、`statuses` の追加のみ直接編集してよい。
- 起票した milestone・タスクを自分で `To Do` に上げない。承認は人間の役割である。
- 依存グラフに循環を作らない（同一リポジトリ内の `--dep`）。起票前に依存の向きを確認する。
- 監査の中でコードを変更しない。修正は起票したタスクの実行として行われる。
- 未確認の推測を起票しない。根拠のない指摘は、起票しないより悪い。
- `improvement-scout`・`improvement-scout-major`・`improvement-dispatch`・`improvement-work`・
  `select-next-task` を変更しない。既存の依存解決ロジックのみでこのスキルの出力を消化できる。

加えて、本スキル固有の禁止事項：

- **リポジトリ間の依存順序を自動で強制する仕組みを作らない。** 新しいラベル解釈ロジックを
  dispatch 側に足したり、あるリポジトリの状態を理由に別リポジトリのタスク作成・承認を機械的に
  ブロックするスクリプトを作ったりしない。順序の担保は description の「## クロスリポジトリ依存」
  節と、手順7の報告文だけに委ねる。
- **あるリポジトリの承認状況を理由に、別リポジトリのタスクを勝手に `To Do` へ進めない。** 上流の
  milestone が `Done` になったことを確認しても、それを理由に下流タスクを自動で `To Do` に上げない。
  承認はあくまで人間が各リポジトリで個別に行う。
- 1リポジトリに閉じる規模の候補を、このスキルで起票しない（起票せず報告するだけにとどめる）。
- ワークスペース全体で1つのタスク一覧を扱っているかのように振る舞わない（各リポジトリの
  `.backlog/` は独立している）。相関ラベルと milestone 名の対応はあくまで人間が横断的に検索する
  ための手がかりであり、backlog CLI 自体がリポジトリをまたいで何かを解決するわけではない。
- opt-in 済みリポジトリの判定基準（`.claude/skills/improvement-scout-major` シンボリックリンクの
  有無）を独自に変えたり、新しいマーカーファイルを作ったりしない。
