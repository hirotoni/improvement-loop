# 改善観点リスト（大規模改善向け）

`improvement-scout-major` が調査の切り口として使う固定リスト。
1 回の探索でこの中から観点を選ぶ制限は設けない。7 観点すべてを対象に、milestone に値する候補があるかを見る。

各観点は次の形式で書かれている。

- **スラッグ**：milestone・タスクに付けるラベルは `viewpoint:<スラッグ>` とする。観点ごとの起票履歴はこのラベルで追える。
- **問い**：その観点でコードベースに投げる具体的な問い。ここに答えられない指摘は起票しない。
- **除外**：この観点で拾ってはいけないもの。1 タスクで完結する規模のものは、この観点であっても `improvement-scout` に譲る（起票しない）。

観点を増やすときは同じ形式で追記する。スラッグは変えない。変えると過去の起票履歴と繋がらなくなる。

`improvement-scout` の 13 観点とは対象規模が異なる。同じジャンルの問題でも、1 タスクで実装まで完結する規模なら `improvement-scout` の対象であり、複数タスクへの分割と依存関係の設計が要る規模だけがこのリストの対象になる。境界はジャンル単独ではなく、ジャンル＋規模の複合で引く。

---

## module-boundary

モジュール・コンポーネント間の責務境界の再編。

- **問い**：ある責務が本来の置き場所ではないモジュールに漏れ出しており、複数のモジュールにまたがる再配置が要るか。
- **問い**：あるモジュールの変更が、契約上は無関係なはずの他モジュールの実装を連鎖的に変えさせているか。その連鎖を断つには境界の引き直しが要るか。
- **問い**：責務の再編を安全に進めるには、どの順序でどのモジュールから手を入れる必要があるか（後続が前提とする中間状態は何か）。
- **除外**：1 つのモジュール・1 つのファイルの内部だけで完結する責務の整理（関数分割、private 化）。これは `improvement-scout` の `duplication` 観点等に譲る。
- **除外**：命名や配置の好みに基づく再編。実際の変更連鎖や事故実績を示せないもの。

## state-model-integrity

システム全体を貫く状態遷移モデルの整合性。

- **問い**：状態（ステータス、フラグ、フェーズ）を管理する複数の主体（スクリプト、設定、外部ツール）は、同じ遷移図を前提にしているか。前提がずれている遷移はどこか。
- **問い**：ある状態から別の状態への遷移が、複数の箇所で別々に判定・実行されており、片方だけ更新すると矛盾した状態が作れてしまう箇所はどこか。
- **問い**：新しい状態や遷移を安全に導入するには、既存のどの参照箇所を漏れなく洗い出して合わせて直す必要があるか。
- **除外**：単一の遷移の分岐条件のバグ修正や、1 箇所のガード漏れの追加。影響範囲が 1 タスクで閉じるものは `improvement-scout` の `broken-behavior` 等に譲る。
- **除外**：モデル自体は整合しているが、メッセージや表示だけが分かりにくいもの。

## cross-cutting-contract

複数コンポーネントが暗黙に依存する契約（引数形式・出力フォーマット・ファイルレイアウト等）の変更。

- **問い**：ある出力フォーマットやファイルレイアウトを、生成側と消費側の複数コンポーネントがそれぞれ独自に前提として埋め込んでいて、契約を変えるなら全消費側を洗い出して合わせて直す必要があるか。
- **問い**：契約が暗黙（ドキュメント化されていない、型やスキーマで縛られていない）であるために、片方だけの変更が他方を静かに壊せる状態になっているか。
- **問い**：契約を移行するとき、新旧の契約が一時的に併存する期間の互換性をどう設計するか。
- **除外**：1 つの呼び出し元・1 つの消費側だけを直せば閉じる契約のずれ。これは `improvement-scout` の `config-inconsistency` 等に譲る。
- **除外**：契約自体は明示的（型定義、スキーマ、公開 API ドキュメント）で、実装が単に追随していないだけのもの（追随は 1 タスクで閉じる）。

## data-schema-migration

データ形式・設定スキーマの移行設計（後方互換性・移行手順）。

- **問い**：既存データ・設定ファイルの形式を変えるとき、既に本番や利用者の手元に存在するデータをどう新形式へ移行するか、その手順は設計されているか。
- **問い**：移行の途中でツールのバージョンが混在する期間（新旧のツールが同じデータを読む状況）が生じるか。生じるならどちらの互換性を保つか。
- **問い**：移行が失敗した・中断した場合に、データが壊れた状態のまま残らないか。ロールバックの経路はあるか。
- **除外**：新規フィールドの追加など、後方互換性が自明で移行手順が要らない変更。これは `improvement-scout` に譲る。
- **除外**：単一のファイル・単一の設定キーの形式修正で、既存データへの影響が無い、または対象データが存在しないもの。

## deterministic-vs-agentic-split

決定論的に処理すべき手順と AI の都度判断に委ねる手順の分離。

- **問い**：本来は決定論的に（スクリプトや固定ロジックで）処理できる手順を、AI エージェントの都度の判断に委ねており、実行のたびに結果がぶれ得る箇所はどこか。
- **問い**：AI の判断に委ねている手順の中に、境界条件やフォーマットさえ決めれば機械的に切り出せる部分はあるか。
- **問い**：決定論的な処理と AI 裁量の処理が 1 つの手順・1 つのスキルの中に混在していて、どこまでが機械的でどこからが判断かの境界が曖昧になっている箇所はどこか。
- **除外**：AI 裁量に委ねる設計が既に明示的で、その理由（曖昧さを含む判断が本質的に必要）が説明できるもの。
- **除外**：1 つの分岐・1 つのコマンド呼び出しをスクリプト化するだけで閉じる小さな機械化。これは `improvement-scout` に譲る。

## pipeline-restructuring

複数ステップから成る内部処理フロー自体の再設計（CI/CD は含まない）。

- **問い**：複数ステップから成る内部処理フロー（例：オーケストレータのループ構造、複数フェーズにまたがる処理の順序）が、ステップ間の暗黙の前提に依存していて、1 ステップの変更が他ステップの前提を壊せる構造になっているか。
- **問い**：フローの一部を差し替える・並び替えるには、複数のステップを横断して合わせて直す必要があるか。
- **問い**：現在のフロー構造では表現できない要件（分岐、並行、再試行）が既に必要とされているか。
- **除外**：CI/CD のパイプライン（ビルド・検証・デプロイの段階構成）は `cicd-architecture` の対象であり、ここでは扱わない。
- **除外**：1 つのステップの内部ロジックの改善で、ステップ間の順序や契約に変更が及ばないもの。これは `improvement-scout` に譲る。

## cicd-architecture

検証・ビルド・デプロイのパイプライン設計（ステージ構成、ゲート設計、pre-commit/CI/CD の役割分担そのものの妥当性）。

- **問い**：検証・ビルド・デプロイの各ステージの役割分担（pre-commit で何を防ぎ、CI で何を防ぎ、デプロイ時に何を防ぐか）は、重複や抜けなく設計されているか。
- **問い**：あるステージのゲート（何が通れば次に進めるか）を変えるには、他のステージの設計も合わせて見直す必要があるか。
- **問い**：パイプライン全体の構成を変えずには解消できない、繰り返し起きている検証漏れや検証の重複はあるか。
- **除外**：`pipeline-restructuring` は内部処理フローを扱い、ここでは扱わない。両者は独立した観点である。
- **除外**：1 つのチェックの追加・修正や、1 つのステージ内の 1 ステップの調整で閉じるもの。これは `improvement-scout` の `missing-detection` 等に譲る。
