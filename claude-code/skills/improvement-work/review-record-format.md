# レビュー記録の書式（正本）

improvement-work 手順 6 がレビューを 1 巡行うたびに notes へ残す記録の書式と、その記録を照合する規則の正本。
書き手の `improvement-work/SKILL.md` 手順 6 と、読み手の `improvement-dispatch/SKILL.md` 手順 6 は、書式を手元に複製せずこのファイルを参照する。
照合の機械的な部分は `claude-code/skills/improvement-dispatch/scripts/check-review-records` が実装している。
書式を変えるときは、このファイル・スクリプト・`tests/test_check_review_records.sh` を同時に直す。

## 書式

1 巡につき 1 つの記録を、`backlog task edit TASK-<n> --append-notes` で notes に追記する。
`<…>` は書き込む内容の説明で、`独立サブエージェント | 自己レビュー` はどちらか一方を書く。
improvement-work 手順 6 の append-notes の例は、この 5 行と一字一句同じにしてある（`tests/test_check_review_records.sh` が検査する）。

```text
### レビュー <巡数> 巡目
- 方法: 独立サブエージェント | 自己レビュー
- 自己レビューにした理由: <Agent ツールが無い / Agent ツールの呼び出しが 2 回続けて失敗した（各回のエラー内容）。独立サブエージェントなら「該当なし」>
- 結果: P0 <件数> / P1 <件数> / P2 <件数> / P3 <件数>（指摘が無ければ No findings）
- 対応: <直した指摘と直し方。見送った P3、妥当でないと判断した指摘とその根拠>
```

- 見出しは `### レビュー <巡数> 巡目` とする。巡数は 1 から数える半角の整数で、前後に半角スペースを 1 つずつ置く。
- 本文は上の 4 行をこの順に書く。各行は `- <項目名>: ` で始める（半角のハイフン・コロン・スペース）。
- 照合が必須とするのは `方法:` と `結果:` の 2 行だけである。「自己レビューにした理由」と「対応」は書くべき行だが、欠けていても照合はそれを書式の崩れとして扱わない。ただし `自己レビュー` の巡で理由の行が無い（または空の）ときは、理由の妥当性を判断できない旨を書式の崩れとして名指しする。`対応:` より前の行の順序は照合では検査しない。`対応:` より後に書いた項目行は読まない（下の `対応:` の続け方を参照）。
- `方法:` の値は `独立サブエージェント` か `自己レビュー` のどちらかをそのまま書く。
- `結果:` の値は `P0 <件数> / P1 <件数> / P2 <件数> / P3 <件数>`（件数は半角の整数、区切りは ` / `）か、指摘が 1 件も無いときの `No findings` のどちらかにする。件数はレビュー役が返した指摘をそのまま数える。妥当でないと判断した指摘や、取り下げられた指摘も件数から除かない。
- レビュー役が取り下げた指摘は、`対応:` に指摘ごとに「取り下げ」の語を含めて書く（例: `P2（…）→ 却下の根拠を渡し、レビュー役が取り下げた`）。照合はこの語で取り下げの記載を見つける。
- `対応:` 以外の 3 行は 1 行に収める。自己レビューにした理由に 2 回分のエラー内容を写すときも、要約するか `；` で区切って 1 行にする。照合は項目名で始まらない行を、`対応:` の続きとして以外は読まない。
- `方法:` と `結果:` の値の後ろには、全角括弧の注記 `（…）` を付けてよい。値が `）` で終わるとき、最初の `（` から後ろを注記とみなす（例: `P0 0 / P1 0 / P2 0 / P3 2（前巡の P2 は解消と評価）`）。照合は注記を除いた値を読む。注記以外の表記揺れ（全角のコロン、区切りの ` / ` の欠落、件数の言い換えなど）は書式の崩れになる。
- `対応:` は最後の行なので、長くなれば次の行へ続けてよい。続きの行は空行を挟まずに書く。`- ` の箇条書きで続けてもよい。`対応:` の後に空行か項目行が来たら、そこから次の `### ` 見出しまでは記録の外（見出しを付けずに追記された検証の記録など）とみなし、照合では読まない。
- `対応:` の行が無い記録も、項目行の後の最初の空行で終わる。記録の後に見出しを付けずに別の notes を追記するときは、空行を挟む。
- 例（TASK-117 の実記録）:

  ```text
  ### レビュー 4 巡目
  - 方法: 独立サブエージェント
  - 自己レビューにした理由: 該当なし
  - 結果: P0 0 / P1 0 / P2 0 / P3 3
  - 対応: P3 3件とも修正（…）。修正後 bash tests/run.sh PASS 563 / FAIL 0。
  ```

## 照合の規則

照合の対象は、notes で `### 引き渡し` が最後に現れる位置より後にある記録だけである（`### 引き渡し` が無ければ notes 全体）。
再引き渡しでは前回分の記録が notes に残り、巡数が 1 から数え直されることもあるためである。
見出しが `巡目` で終わる記録と、見出しが `レビュー <数>` で始まる記録をレビュー記録として扱う（形が崩れていれば書式の崩れとして名指しする）。
対象の記録のうち notes で最後に現れるものを最終巡とする。
既知の限界として、`2 巡目のレビュー` のように `巡目` で終わらず `レビュー <数>` でも始まらない見出しは、レビュー記録として数えられない。それが実際の最終巡なら、その前の巡が最終巡として扱われる。見出しは書式どおりに書くこと。

レビュー記録は improvement-work の自己申告であり、照合で保証できるのは記録の書き忘れと、書かれた件数から分かる停止条件の未達までである。
そのため、`RESULT` だけで To Do への差し戻しの根拠になるのは `NO_RECORDS` と `NOT_CONVERGED` の 2 つだけにしている（`NEEDS_REVIEW` は下の「スクリプトが判定しないもの」の判断次第）。
書式の崩れは差し戻しの根拠にせず、`FORMAT_WARNING:` の行で巡を名指しして報告に載せるだけにする。
書式の崩れで実装・レビュー済みのタスクをやり直させると、記録の書き方だけで `max_redispatch` を消費するためである。

書式の崩れとして名指しするのは次のものである。

- 見出しが `レビュー <巡数> 巡目` の形ではない。
- `方法:` または `結果:` の行が無い、または 2 行以上ある。
- `方法:` の値が `独立サブエージェント` と `自己レビュー` のどちらでもない。
- `結果:` の値が件数として読めない。
- `自己レビュー` の巡で、「自己レビューにした理由」の行が無い、または空である。理由の妥当性を確かめられないので、名指しの末尾に `（未照合）` を付ける。
- `方法:` が読めない（行が無い・重複・値が 2 値以外）。自己レビューの巡かどうかを確かめられないので、その旨を `（未照合）` を付けて別の行で名指しする。最終巡で取り下げの記載があるときは、`NEEDS_REVIEW:` の行に独立サブエージェントの巡であることも確かめる旨を添える。
- 最終巡の `結果:` が読めない。このときは停止条件を機械的に確かめられないので、`NOT_CONVERGED` にはせず、その旨を `（未照合）` を付けて名指しする。

`（未照合）` で終わる `FORMAT_WARNING:` の行は、照合が確かめられなかったことを示す。読み手はこの行を報告の「人間に必要な行動」に載せる。

`check-review-records` は次の順に判定し、最初に当たったものを `RESULT` にする。

| 順 | `RESULT` | 終了ステータス | 条件 |
| --- | --- | --- | --- |
| 1 | `NO_RECORDS` | 3 | 対象のレビュー記録が 1 巡も無い。レビュー未実施として扱う。 |
| 2 | `NOT_CONVERGED` | 1 | 最終巡の `結果:` が件数として読め、`P0`/`P1`/`P2` が 1 件以上あり、取り下げの記載が無い。または最終巡が `自己レビュー` で `P0`/`P1`/`P2` が 1 件以上ある（自己レビューの巡では取り下げを認めない）。 |
| 3 | `NEEDS_REVIEW` | 5 | 要確認の巡がある。`NEEDS_REVIEW:` の行（文章の意味を読む必要がある巡。`自己レビュー` の巡で理由が書かれている、または最終巡（`自己レビュー` 以外）の `P0`/`P1`/`P2` が 1 件以上あり `対応:` に取り下げの記載がある）か、`FORMAT_WARNING:` の行（書式の崩れ）が 1 行以上ある。 |
| 4 | `OK` | 0 | 上のどれにも当たらない。最終巡の `P0`/`P1`/`P2` が 0 件（または `No findings`）で、自己レビューの巡も書式の崩れも無い。 |
| - | `ERROR` | 2 | 引数の誤り、`backlog task view` の失敗など。 |

スクリプトが判定しないもの（`NEEDS_REVIEW` のときに読み手の AI が判断する範囲）は次の 2 つだけである。

- `自己レビュー` の巡の「自己レビューにした理由」が、improvement-work 手順 6 の 2 条件（Agent ツールが自分のツール一覧に無い／Agent ツールの呼び出しが 2 回続けて失敗し、各回の失敗内容が書かれている）のどちらかに当たるか。理由の行が無い・空の巡はこの判断の対象にせず、`FORMAT_WARNING:` の行で報告に載せるだけにする。
- 最終巡の `P0`/`P1`/`P2` のすべてについて、独立サブエージェントのレビュー役が取り下げたと指摘ごとに書かれているか。取り下げと書かれていない指摘が 1 件でもあれば停止条件に達していない。直したと書かれているだけの指摘は再レビューを経ていないので残っているものとして数える。

## 出力

標準出力の最終行が `RESULT: <値>` である。その前に次の行を出す。

- `REVIEW_ROUNDS: <件数>`：対象のレビュー記録の数。
- `FINAL_ROUND: <見出し>` と `FINAL_RESULT: <結果の値>`：最終巡の見出しと `結果:` の値（読めたときだけ）。
- `NOT_CONVERGED: <見出し>: <理由>`：停止条件に達していない理由。
- `NEEDS_REVIEW: <見出し>: <確認すること>`：AI が判断する巡ごとに 1 行。
- `FORMAT_WARNING: <見出し>: <理由>`：書式の崩れごとに 1 行。報告に載せるだけで、差し戻しの根拠にしない。照合で確かめられなかったものは末尾が `（未照合）` になる。

診断メッセージは標準エラーに出す。
