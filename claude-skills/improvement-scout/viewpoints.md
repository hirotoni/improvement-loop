# 改善観点リスト

`improvement-scout` が調査の切り口として使う固定リスト。
1 回の探索ではこの中から 3 観点を選ぶ。

各観点は次の形式で書かれている。

- **スラッグ**：タスクに付けるラベルは `viewpoint:<スラッグ>` とする。観点ごとの起票履歴はこのラベルで追える。
- **問い**：その観点でコードベースに投げる具体的な問い。ここに答えられない指摘は起票しない。
- **除外**：この観点で拾ってはいけないもの。

観点を増やすときは同じ形式で追記する。スラッグは変えない。変えると過去の起票履歴と繋がらなくなる。

---

## broken-behavior

壊れている処理。

- **問い**：どの入力・環境・順序でこの処理は失敗するか。失敗したとき利用者に何が見えるか。
- **問い**：正常系しか想定していない分岐はどこか。空、未設定、初回実行、権限なしの場合はどうなるか。
- **除外**：再現条件を言えないもの。「危なそう」で止まる指摘。

## doc-drift

宣言と実態の乖離。

- **問い**：README や CLAUDE.md に書かれた手順を今そのまま実行して通るか。
- **問い**：セットアップスクリプトが列挙している対象と、実際に存在するディレクトリ・パッケージは一致しているか。
- **問い**：lock ファイルやバージョン pin と、宣言側の指定はずれていないか。
- **除外**：表現の好み、記述の薄さ。実行して食い違う点だけを扱う。

## config-inconsistency

設定の不整合。

- **問い**：同じ設定が複数箇所で宣言されていないか。どちらが勝つか説明できるか。
- **問い**：参照先が存在しないパス、コマンド、プラグイン名はないか。
- **問い**：無効化されたまま忘れられた設定、到達しない分岐はないか。
- **除外**：意図的な上書き。git log で意図が確認できるものは除く。

## error-handling

失敗時の扱いと後始末。

- **問い**：失敗が黙って捨てられている箇所はどこか（終了コードを見ていない、出力を捨てている）。
- **問い**：途中で失敗したとき、中間状態（部分的なリンク、バックアップ、一時ファイル）が残らないか。
- **問い**：シェルスクリプトに `set -euo pipefail` 相当があるか。ない場合、どの行が黙って進むか。
- **除外**：失敗しても影響がない箇所への防御追加。

## env-assumptions

環境前提の埋め込み。

- **問い**：ハードコードされた絶対パス、ユーザー名、ホスト名はないか。
- **問い**：前提しているコマンドの存在確認をしているか。ない環境で何が起きるか。
- **問い**：OS やアーキテクチャに依存する分岐が、その前提を明示しているか。
- **除外**：この環境専用と明示されている箇所への一般化提案。

## idempotency

再実行したときの安全性。

- **問い**：セットアップやインストールを 2 回目に流したとき、1 回目と同じ結果になるか。
- **問い**：既存ファイルを退避する処理は、退避先が既に存在する場合に壊れないか。
- **問い**：中断してから再実行したとき、前回の中間状態を正しく扱えるか。
- **除外**：一度しか実行しない前提が明示されている処理。

## secrets-permissions

秘密情報と権限。

- **問い**：資格情報、トークン、個人情報が追跡対象に入っていないか。ignore 設定は実際に効いているか。
- **問い**：外部から取得したスクリプトを検証なしで実行している箇所はないか。
- **問い**：生成されるファイルのパーミッションは必要最小か。
- **除外**：公開前提の設定値。

## missing-detection

壊れ方を検知する手段の欠落。

- **問い**：壊れやすい箇所（生成物、外部依存、環境差）に、壊れたことを知る仕組みがあるか。
- **問い**：pre-commit や CI が宣言しているチェックは、実際に壊れを捕まえられるか。
- **除外**：「テストを書く」で終わる提案。何の壊れ方を検知したいのかを書けないものは起票しない。

## dependency-hygiene

依存とバージョン管理。

- **問い**：宣言されている依存は今も使われているか。使われていない宣言はどれか。
- **問い**：バージョンが固定されているものと浮いているものの基準は一貫しているか。
- **問い**：更新手順が書かれているか。更新後の検証手段があるか。
- **除外**：単なるバージョン上げ。壊れる根拠か運用上の問題を示せるものだけ扱う。

## deprecated-api

廃止・非推奨 API の使用。

- **問い**：非推奨として警告が出る呼び出しを使っていないか。
- **問い**：置き換え先が判明していて、移行しても挙動が変わらないと言えるか。
- **除外**：置き換え先が不明なもの。挙動差の確認ができないもの。

## duplication

重複と責務の混在。

- **問い**：同じロジックが複数箇所にあり、片方だけ直る事故が起きうる箇所はどこか。
- **問い**：1 つのファイル・関数が担っている責務は説明できる数に収まっているか。
- **除外**：見た目が似ているだけで、変更理由が異なるコード。共通化の提案そのものが目的の指摘。

## startup-cost

起動時間と読み込みコスト。

- **問い**：起動時に必要でない処理を同期実行していないか。測った根拠はあるか。
- **問い**：遅延読み込みできる宣言が即時読み込みになっていないか。
- **除外**：測定していない体感ベースの指摘。数 ms 単位の最適化。

## daily-friction

日常操作の摩擦。

- **問い**：キーマップやエイリアスが衝突・重複していないか。後勝ちで意図せず潰れているものはないか。
- **問い**：頻繁に使う操作が、余計な手数を要求していないか。
- **問い**：エラー時のメッセージから、次に何をすればいいか分かるか。
- **除外**：好みの割り当て変更。衝突や欠落といった客観的な問題に限る。
